IV. Résumé du projet Guardian Ledger

Contexte et genèse du projet

Destiny 2 est un jeu de tir à la première personne développé par Bungie, dont la particularité est de posséder un système d'inventaire très riche : armes, armures, objets de classe, mods, matériaux… Chaque joueur possède jusqu'à 3 personnages (Titan, Chasseur, Arcaniste), chacun avec son propre équipement, et un coffre partagé pouvant contenir des centaines d'objets.

Bungie met à disposition une API REST publique (https://www.bungie.net/Platform) permettant d'accéder, via OAuth 2.0, aux données d'un joueur authentifié. Cette API expose notamment :

  • Le profil du joueur (/Destiny2/[membershipType]/Profile/[membershipId]/)
  • L'inventaire de chaque personnage et du coffre
  • Les définitions d'objets via le Manifeste Destiny 2 (base de données SQLite téléchargeable)

Le problème : l'interface officielle de Bungie (DIM, Destiny Item Manager) est complexe et lourde. Il n'existe pas d'outil minimaliste permettant de visualiser son inventaire de façon claire et rapide.

La solution Guardian Ledger : une application légère, claire, centrée sur l'essentiel.

Objectifs du produit

  1. Permettre à un joueur de créer un compte Guardian Ledger (email + mot de passe)
  2. Lier son compte Bungie via le protocole OAuth 2.0
  3. Consulter son Dashboard : personnages actifs avec leur niveau de puissance
  4. Consulter son Coffre (Vault) : liste complète des objets avec filtrage par type (armes / armures) et par rareté

Fonctionnalités clés

Authentification double-couche

L'application met en œuvre une authentification à deux niveaux :

  1. Compte applicatif (email + mot de passe hashé avec bcryptjs, JWT émis par l'API)
  2. Liaison Bungie via OAuth 2.0 : l'utilisateur autorise Guardian Ledger à accéder à ses données Destiny 2. Un access_token et un refresh_token sont stockés en base, avec renouvellement automatique avant expiration.

Dashboard

Affichage des personnages du joueur :

  • Nom du personnage (race + classe)
  • Niveau de puissance (Power Level)
  • Icône de classe

Coffre (Vault)

Liste paginée des objets du coffre :

  • Icône, nom, type d'emplacement (Cinétique, Énergie, Puissance, Casque, Torse…)
  • Niveau de puissance de l'objet
  • Rareté colorée (Exotique, Légendaire, Rare…)
  • Filtres : Armes / Armures / Tout

Résolution des définitions via le Manifeste local

Les objets Bungie sont identifiés par des hash numériques (ex. 1087279994). Guardian Ledger embarque le Manifeste Destiny 2 (base SQLite locale, ~300 Mo) et interroge la table DestinyInventoryItemDefinition pour résoudre chaque hash en nom, icône et métadonnées d'affichage.

VII. Réalisation personnelle — Authentification OAuth 2.0 Bungie

Présentation de la fonctionnalité

Je vais présenter le flux d'authentification OAuth 2.0 que j'ai implémenté pour lier le compte Guardian Ledger d'un joueur à son compte Bungie.net. C'est la fonctionnalité la plus complexe du projet, car elle implique plusieurs échanges sécurisés entre le frontend, le backend et les serveurs Bungie.

Problématique

L'API Bungie exige que chaque accès aux données personnelles d'un joueur soit précédé d'une autorisation OAuth 2.0 de sa part. Ce n'est pas une simple clé API : il faut que l'utilisateur clique sur "Autoriser" sur le site Bungie.net, puis que l'application récupère un code d'autorisation éphémère et l'échange contre un access_token et un refresh_token.

Flux OAuth 2.0 implémenté

Étape 1 — Redirection vers Bungie

Lorsqu'un utilisateur s'inscrit ou se connecte sans compte Bungie lié, le backend renvoie un tempToken JWT (valide 10 minutes). Le frontend redirige alors l'utilisateur vers :

https://www.bungie.net/en/OAuth/Authorize?client_id=CLIENT_ID&response_type=code&state=tempToken

Le state contient le tempToken, ce qui permet de retrouver l'utilisateur lors du callback.

Étape 2 — Callback

Bungie redirige l'utilisateur vers GET /api/auth/bungie/callback?code=XXX&state=tempToken. Le backend :

  1. Vérifie et décode le tempToken pour récupérer le userId
  2. Échange le code contre des tokens via POST https://www.bungie.net/platform/app/oauth/token/
  3. Récupère le bungieMembershipId et le displayName du joueur
  4. Stocke les tokens en base via Prisma
  5. Émet le JWT final (appToken) et redirige vers le frontend

Étape 3 — Renouvellement silencieux

À chaque appel aux routes /api/me/*, la fonction ensureFreshToken() vérifie si le access_token expire dans moins de 5 minutes. Si c'est le cas, elle effectue un appel de renouvellement transparent vers Bungie et met à jour la base de données, sans que l'utilisateur en soit conscient.

// Extrait de routerMe.js — renouvellement automatique du token Bungie
async function ensureFreshToken(user) {
    const now = new Date();
    const expiresAt = user.bungieTokenExpiresAt
        ? new Date(user.bungieTokenExpiresAt)
        : null;

    // Token encore valide : on le retourne directement
    if (expiresAt && now < new Date(expiresAt.getTime() - 5 * 60 * 1000)) {
        return user.bungieAccessToken;
    }

    // Renouvellement via refresh_token
    const params = new URLSearchParams({
        grant_type:    'refresh_token',
        refresh_token: user.bungieRefreshToken,
        client_id:     process.env.CLIENT_ID,
        client_secret: process.env.CLIENT_SECRET,
    });

    const tokenRes = await axios.post(
        'https://www.bungie.net/platform/app/oauth/token/',
        params,
        { headers: { 'Content-Type': 'application/x-www-form-urlencoded',
                     'X-API-Key': process.env.BUNGIE_API_KEY } }
    );

    // Mise à jour en base de données
    await prisma.user.update({
        where: { id: user.id },
        data: {
            bungieAccessToken:    tokenRes.data.access_token,
            bungieRefreshToken:   tokenRes.data.refresh_token,
            bungieTokenExpiresAt: new Date(Date.now() + tokenRes.data.expires_in * 1000),
        },
    });

    return tokenRes.data.access_token;
}

Sécurité

  • Les tokens Bungie sont stockés côté serveur (jamais exposés au frontend)
  • Le JWT_SECRET est chargé depuis les variables d'environnement (.env, hors versioning)
  • Le middleware requireAuth vérifie systématiquement la validité du JWT avant tout accès aux routes protégées

IX. Veille sur les vulnérabilités de sécurité du projet

1. Introduction

Dans le cadre du développement de Guardian Ledger, j'ai mené une veille active sur les vulnérabilités de sécurité pouvant impacter une application Node.js/Express intégrant une authentification OAuth 2.0 et stockant des tokens d'accès à des services tiers.

2. Méthodologie de veille

Ressources utilisées :

  • OWASP Top Ten : référence internationale pour les failles des applications web
  • Documentation officielle Express (sécurité en production)
  • Documentation Bungie API (bonnes pratiques OAuth)

Mots-clés de recherche : "JWT security Node.js", "OAuth 2.0 token storage best practices", "Express CORS security"

3. Vulnérabilités identifiées et traitées

A. Exposition du JWT_SECRET

Risque : Si le JWT_SECRET est codé en dur dans le code source ou versionné, un attaquant peut forger des tokens JWT valides et usurper l'identité de n'importe quel utilisateur.

Solution appliquée : Le secret est chargé depuis la variable d'environnement process.env.JWT_SECRET. Le fichier .env est listé dans .gitignore et n'est jamais commité.

const JWT_SECRET = process.env.JWT_SECRET || 'guardian-ledger-dev-secret-changeme';

⚠️ La valeur de fallback 'guardian-ledger-dev-secret-changeme' est uniquement destinée au développement local. En production, JWT_SECRET doit impérativement être défini dans les variables d'environnement.

B. Stockage des tokens Bungie côté serveur

Risque : Si les access_token et refresh_token Bungie étaient stockés côté client (localStorage), ils pourraient être volés via une attaque XSS.

Solution appliquée : Les tokens Bungie sont exclusivement stockés en base de données côté serveur. Le frontend ne reçoit que le JWT applicatif (appToken), qui ne contient pas les tokens Bungie.

C. Validation stricte des entrées utilisateur

Risque : Injections et données malformées sur les routes d'authentification.

Solution appliquée : Validation systématique des champs email et password à l'entrée de chaque route :

if (!email || !password)
    return res.status(400).json({ error: 'Email et mot de passe requis.' });
if (!/^[^\s@]+@[^\s@]+\.[^\s@]+$/.test(email))
    return res.status(400).json({ error: 'Email invalide.' });
if (password.length < 8)
    return res.status(400).json({ error: 'Mot de passe trop court (min 8 caractères).' });

D. Protection contre les injections SQL (Manifeste)

Risque : La construction dynamique du nom de table dans manifestService (SELECT json FROM ${tableName} WHERE id = ?) pourrait être vecteur d'injection si tableName provenait d'une entrée utilisateur.

État : tableName est uniquement fourni par le code interne (jamais par l'utilisateur). La valeur de id est passée en paramètre préparé (stmt.get(id)), ce qui protège contre l'injection SQL.

4. Conclusion sécurité

La conception de Guardian Ledger intègre les bonnes pratiques de sécurité dès la conception (Security by Design) : séparation des secrets, tokens serveur-side, validation des entrées, requêtes préparées. Ces mesures couvrent les risques les plus critiques de l'OWASP Top 10 applicables au projet (A02 – Cryptographic Failures, A03 – Injection, A07 – Identification and Authentication Failures).

X. Description d'une situation de travail ayant nécessité une recherche

La résolution des hash Destiny 2 en entiers 32-bit signés

Le besoin

Lors de l'intégration du Manifeste Destiny 2, j'ai rencontré un problème inattendu : les réponses de l'API Bungie retournent des hash d'objets non signés sur 32 bits (exemple : 3245015_83), mais la base SQLite du Manifeste stocke ces mêmes identifiants comme des entiers signés sur 32 bits (exemple : -1049951413).

Un simple WHERE id = 3245015_83 ne retournait donc aucun résultat.

La recherche

J'ai recherché sur Google avec les mots-clés : "bungie manifest hash sqlite signed integer".

J'ai découvert sur les forums de développeurs Bungie et sur Stack Overflow que c'est un comportement documenté et connu : le Manifeste utilise des entiers 32-bit signés pour des raisons historiques liées à SQLite, tandis que l'API renvoie les hashes non signés.

La solution

La conversion s'effectue avec l'opérateur de décalage de bit >> 0 en JavaScript, qui force la conversion d'un entier non signé en entier signé 32-bit :

// src/backend/services/manifestService.js
const getDefinition = (tableName, hash) => {
    try {
        // Conversion du hash non signé (API Bungie) en entier 32-bit signé (SQLite)
        const id = hash >> 0;
        const stmt = db.prepare(`SELECT json FROM ${tableName} WHERE id = ?`);
        const row = stmt.get(id);
        return row ? JSON.parse(row.json) : null;
    } catch (error) {
        console.error("Erreur SQL:", error);
        return null;
    }
};

Exemple :

  • Hash reçu de l'API : 0xFFFFFF00 (= 4294967040 en non signé)
  • Après >> 0 : -256 (entier 32-bit signé)
  • Requête SQL : SELECT json FROM DestinyInventoryItemDefinition WHERE id = -256 ✓

XI. Bilan et perspectives du projet

Bilan

Guardian Ledger m'a permis de mettre en pratique, sur un projet concret et fonctionnel, l'ensemble des compétences du référentiel CDA. La principale valeur du projet réside dans la complexité réelle qu'il implique : l'intégration d'une API tierce avec OAuth 2.0, la gestion du renouvellement silencieux de tokens, l'interprétation d'un manifeste de données massif (300 Mo), et la mise en place d'une suite de tests automatisés complète.

Points de satisfaction :

  • Le flux OAuth 2.0 complet est fonctionnel et sécurisé
  • Les 66 tests automatisés couvrent les cas nominaux et les cas d'erreur
  • L'architecture découplée frontend/backend facilite la maintenabilité

Points d'amélioration identifiés :

  • La gestion du Manifeste (téléchargement, vérification de version) pourrait être automatisée via une tâche planifiée (CRON)
  • L'interface Vault mériterait un système de pagination côté backend pour les coffres très fournis
  • La couverture de tests frontend pourrait être étendue aux vues Dashboard.vue et Vault.vue

Perspectives

Les évolutions envisagées pour Guardian Ledger :

  1. Gestion de plusieurs personnages : pouvoir basculer entre ses 3 personnages et voir l'inventaire de chacun
  2. Transfert d'objets : utiliser l'API Bungie pour transférer des objets entre personnages et coffre
  3. Recherche d'objets : moteur de recherche full-text dans le coffre
  4. Mise en production : déploiement sur un VPS via Docker Compose avec reverse proxy Nginx

XII. Conclusion

Guardian Ledger a représenté un projet de formation particulièrement formateur et stimulant. Sa particularité, par rapport à un projet purement académique, est qu'il s'attaque à une vraie problématique d'intégration avec un système tiers complexe — l'API Bungie — qui impose ses propres contraintes, son propre protocole d'authentification et sa propre modélisation des données.

La conception de l'architecture full-stack, le choix des technologies, la sécurisation de l'authentification, la gestion du manifeste SQLite et la mise en place d'une suite de tests complète m'ont permis de consolider concrètement chacune des onze compétences du référentiel CDA.

Ce projet m'a également appris à rechercher de la documentation technique en anglais, à naviguer dans des APIs tierces mal documentées, et à persévérer face aux problèmes de données inattendus comme la conversion des hashes 32-bit. Ces compétences de débogage et de recherche autonome sont, à mes yeux, aussi importantes que les compétences techniques elles-mêmes.
